# Milestone 6.5 — `openssl`, certificates and TLS: Phase-0 analysis

This is a new kit cycle (PLAYBOOK Phases 0–1) for the parts of NSE that sit
behind `HAVE_OPENSSL`:
- the `openssl` Lua module (`nse_openssl.cc`);
- certificate parsing (`nse_ssl_cert.cc`);
- TLS sockets (the SSL paths of `nse_nsock.cc` and `nsock/src/nsock_ssl.c`).

It contains the inventory, the C-flaw scan, the threat model and a
dependency-ordered plan. **No port code is written until the decisions in §9
are approved** (kit requirement). Step 0's spikes are scratch Rust, used
only to measure. The oracle harness (Phase 2) and the per-module
six-gate loop follow on approval.

**Where the numbers come from.** Every count below was measured against one
of three things:
- the C tree in this repository;
- the installed `/usr/bin/nmap` (Debian 7.94SVN, OpenSSL 3.0.13);
- nmap 7.99SVN built out of tree from this repository.

None is recalled from memory. Anything that was not verified is marked
**unverified**.

**How the draft was checked.** It was written from six independent
investigations:
- the C surface;
- the TLS surface;
- a corpus census;
- the crate options;
- a C-flaw scan;
- the oracle design.

Three adversarial reviews then attacked it, one each on fidelity, security
and sequencing. They re-measured its central claims and overturned four of
them:
- that nmap skips handshake signature checks;
- that TLS has no socket-I/O drift;
- that `-sC` is helped by M6.5;
- that the threat model's memory budget is active.

§8 records each correction.

> **Status (after M6.6).** D0 (iii), D1 (c), D2 (D) and D4 (b) are
> decided (§9); D3, D10 and D11 are open. D0 put M6.6 first, and it is

## 0. Before M6.5: what "the next milestone" should be

M6-ANALYSIS.md (`:145-147`) put `openssl` before `lpeg`, `lfs`, `zlib` and
`libssh2` because it was "the only other module with real weight (41 hard
requires)". That count is wrong (§8): there are 2 hard requires and 39
`silent_require`s. The order built on it does not survive measurement.

**Measured on the port binary today.** This command ends in `NSE failed to
find nselib/nmapdb.lua … nse_main:918: could not load script … QUITTING!`:

```
nmap-rs --datadir /home/user/nmap -Pn -p 1 -sC 127.0.0.1
```

`--script default`, `version` and `safe` end the same way.
- **Why the gate missed it.** The `-sC` differential runs on a fixture
  datadir (`tests/differential/m6/oracle/gen_m64_cli.py:10-14,59`), so its
  green result does not mean `-sC` works with the shipped scripts.
- **Why the port matches no nmap build here.** In C, `nmapdb`, `lfs` and
  `lpeg` are registered unconditionally (`nse_main.cc:564-567`). Only
  `openssl`, `libssh2` and `zlib` are behind `#ifdef`s (`:568-576`).
  - A port without `openssl` behaves like a real `--without-openssl` build.
  - A port without `nmapdb` or `lpeg` behaves like no build at all.

**Load outcomes by what is ported.** Each cell is LOUD / QUIET:
- **LOUD:** a failed hard `require` that aborts the whole NSE run.
- **QUIET:** a `silent_require` that drops the script.

The method is `m65_census.simulate` over `script.db`'s categories. It
reproduces all 19 library pins in
`1f3184592:nmap-rs/crates/core/tests/nselib_differential.rs:29-49` (17 since
M6.6 step a).

| ported in addition | `default` (127 scripts) | `version` (48) | all 611: OK / LOUD / QUIET |
|---|---|---|---|
| nothing (today) | 9 / 5 | 10 / 0 | 514 / 51 / 46 |
| `openssl` (M6.5 as first drafted) | **9** / 0 | **10** / 0 | 557 / 50 / 4 |
| `nmapdb` | 3 / 6 | 7 / 0 | 531 / 33 / 47 |
| `nmapdb` + `lpeg` | **0** / 6 | **0** / 0 | 560 / 2 / 49 |
| all three | 0 / 0 | 0 / 0 | 606 / 1 / 4 |

**What each candidate costs:**
- **`nmapdb`** is `nse_db.cc` (113 lines). The corpus uses 2 of its 4
  functions, `getservbyport` (`datafiles.lua:83`) and `mac2corp` (`:127`).
  Both run over data the port already parses (`core::macvendor` and the

  - `getprotbynum` and `getprotbyname` need an `nmap-protocols` parser,

**TLS is the other large source of value, and it does not need the

- **Measured on loopback** against `openssl s_server -www` on :443:

  - the port prints nothing.
- **For comparison:** registering `openssl` makes 43 scripts loadable, 5 of
  them `default`.

So the order is a decision (**D0**, §9), not a given.

## 1. Four findings that shape the milestone

### 1.1 The oracle is not this tree's C, and the drift here is real

**The oracle's source.** `/usr/bin/nmap` is Debian
`7.94+git20230807.3be01efb1`, built from commit `3be01efb1` (2023-07-31). The
package carries four patches. The only one that is not packaging, `0002`,
touches only `ncat/ncat_posix.c`, so the oracle's NSE C
is exactly `3be01efb1`.

**Later commits that change the M6.5 surface:**

| commit(s) | change |
|---|---|
| `3d99250c8` | leading-NUL IVs |
| `209da5174` | `nse_openssl_state` |
| `538764bb6` | certificate years and ASN.1 time parsing |
| `082894dca` | TLS security level 0 |
| `633bfe00b` | DTLS |
| `f87c5e20b`, `38823b5cd`, `3a0db5dc5`, `92d5b6a31`, `a86e86913`, `9458beda4`, `3a528e1d1`, `c94d96b65`, `89f0e6267`, `209e5735d` | TLS read and EOF semantics in `nsock_core.c` and `nse_nsock.cc` |

**This is not the first M6 milestone with such drift.** The plain-TCP EOF row
in §2 shows the tree and 7.94 already differed in M6.4. The ledger entry `nse-ops-always-yield`
describes the tree-only `NU_ACTION_IMMEDIATE` as "in nmap". M6.5 is the first
milestone where the drift is large enough to need a policy (**D1**).

### 1.2 The coupling runs one way: "`openssl` loads" ⇒ "TLS works"

**In C, one switch gates all three.** `HAVE_OPENSSL` gates:
- the module (`nse_main.cc:571-573`);
- certificate parsing and TLS sockets (`nse_nsock.cc:473,515,889-909,1220-1229`).

**The corpus reads the module's presence as a promise of TLS.**
- `sslcert.lua` chooses its STARTTLS strategy by whether
  `pcall(require,"openssl")` succeeded (`nselib/sslcert.lua:41,1024`).
- `omp2.lua:36-40,61-65` gates `connect(...,"ssl")` the same way.

**TLS assumes nothing about the module.**
- `comm.lua` has no `openssl` reference.
- `http.lua:155` uses its `have_ssl` only for digest/NTLM authentication
  (`:1419-1440`) and the md5 of 404 bodies (`:2556-2558`).

**Two callers of `get_ssl_certificate` exist:**
- `sslcert.lua:1051,1066`, gated on `have_openssl`;
- `ftp.lua:107-108`, which uses `pcall(socket.get_ssl_certificate, socket)`
  as a probe for "is this socket TLS". `ftp.auth` relies on it (`:147`).

So the contract to keep is:
- raise `bad argument #1 … not a SSL socket` on a plain socket
  (`nse_nsock.cc:890-897`);
- return nil or a table on a TLS socket (`nse_ssl_cert.cc:546-558`).

**Consequences for the order** (D2):
- **Module before TLS is harmful.** It makes the corpus assume TLS that is
  not there:
  - 5 sslcert scripts go from PEM-only results to hard errors (`sslcert.lua:44-66`);
  - ssl-enum-ciphers raises on RSA key exchange (`ssl-enum-ciphers.nse:718-742`);
  - STARTTLS certificate retrieval regresses for 11 services (`sslcert.lua:804-829`, by reading).
- **TLS before the module is harmless, by reading.** `have_openssl` stays
  false, so sslcert keeps its `_WITHOUT_RECONNECT` path.
  - This is not yet measured. Measure it by running `nselib_differential`
    and the script gates with TLS on and `openssl` absent.

### 1.3 No pure-Rust TLS stack does what nmap's does, and "verify nothing" is not what nmap does

**Reach.** The matrix is 21 `openssl s_server` 3.0.13 servers on loopback.

| client | servers reached |
|---|---|
| 7.94 | 15 |
| the tree's C (security level 0) | 21 |
| rustls 0.23.45 | 7 |

**What rustls lacks, by design.** rustls does not support:
- SSL 3, TLS 1.0 and TLS 1.1;
- CBC suites;
- static-RSA key exchange;
- non-RFC-7919 DHE;
- DTLS.

This is a documented design choice (`rustls-0.23.45/src/manual/features.rs:42-63`),
and no crypto provider can add these features.

**The ready-made providers bring C.** ring and aws-lc-rs compile about 230k
and 1.68M lines of C and assembly respectively. That conflicts with M6
Decision 1, "ship no C".

**`SSL_VERIFY_NONE` turns off chain verification only.** In OpenSSL 3.0.13,
only chain verification depends on the verify mode (`statem_clnt.c:1888`).
These checks run regardless:
- every certificate in the chain is parsed (`:1808-1811`);
- each certificate entry must have an exact length (`:1813-1816`);
- the public key must be present (`:1903`) and of a known type (`:1909`);
- in TLS 1.2, the key type must match the suite (`:1918-1922`);
- the ServerKeyExchange signature is verified (`:2302-2306`);
- in TLS 1.3, the CertificateVerify signature is verified (`statem_lib.c:532-538`);
- the server must send `renegotiation_info` (RFC 5746).

**Measured** with a scratch TLS 1.2 server:

| server sends | 7.94 | rustls with an accept-everything verifier |
|---|---|---|
| a ServerKeyExchange with one signature byte flipped | alert 51 | continues |
| a certificate entry with 1 trailing byte | alert 50 | continues |
| an undecodable certificate | alert 42 | continues |
| no `renegotiation_info` | alert 40 | continues |

So "skip verification as nmap does" is wrong. A client that skips handshake
signatures would let `get_ssl_certificate` report a certificate whose key the
peer never proved it holds. That is exactly what `ssl-known-key` and
`ssl-cert` report on.

**Reach is not fidelity either.** Against a server holding an RSA and an
ECDSA certificate (`s_server -dcert`):
- 7.94 offers DHE-RSA first and gets the RSA certificate;
- rustls negotiates ECDHE-ECDSA and gets the ECDSA certificate.

ssl-cert, a `default` script, would therefore print a different certificate.

**The client is a decision of its own.** The legacy-TLS question is **D3**.
It does not fall out of a crate choice, and it is posed only after a spike
(§11, step 0).

### 1.4 The memory budget the threat model leans on is off in the shipped binary

**The binary has no budget.**
- The CLI builds the NSE state with `memory_limit: None` (`1f3184592:nmap-rs/crates/cli/src/nse.rs:258`).
- With no limit, `Budget::allows` always says yes (`crates/vendor/piccolo/src/budget.rs:35-69`).
- The budget sees only what `gc-arena` sees: strings record their heap bytes
  (`crates/vendor/piccolo/src/string.rs:58,67`). A `BIGNUM` holding a `Vec`
  would be invisible.

**Consequence.** A peer-chosen or script-chosen size, such as
`rand_bytes(2^40)` or a huge `bin2bn`, would reach Rust's allocation-failure
handler, which aborts the process.

**Correction for M6.5.** Every such size goes through `stdlib::reserve`
(`1f3184592:nmap-rs/crates/core/src/nse/stdlib/mod.rs:165-174`: budget plus `try_reserve`), and
userdata record their heap bytes with the budget (§6). Whether the CLI should
set a budget at all is recorded as engineering choice E6.

## 2. The oracle and its drift

**Two oracles ran the same probes:**
- the installed 7.94;
- this tree's nmap, built out of tree in about 3 minutes with:

  ```
  git archive HEAD | tar -x
  ./configure --without-zenmap --without-ndiff --without-nping --without-ncat --with-liblua=included --with-libssh2=included
  make nmap
  ```

  The result reports "Nmap 7.99SVN", liblua 5.4.8 and the system OpenSSL 3.0.13.

**Case matrix.** A seeded, table-driven prerule probe with a crash-resuming
driver runs **247,238 cases in 16.4 s**:
- 161,435 ok, 85,795 errors, 8 crashes. Of the errors, 80,407 are
  `OpenSSL error:` messages; the other 5,388 are the port's own messages
  (`Unknown cipher/digest algorithm`, argument errors);
- no target needed: a prerule with zero targets exits rc=0 in 0.09 s.

**Certificate corpus.** 2,876 DER certificates:
- 1,092 OIDs, used both as subject attributes and as extensions;
- 11 string tags;
- time edge cases;
- 18 key types × 13 extensions;
- 143 truncations and 400 byte flips.

The corpus runs in 2.6 s, and two oracle runs give identical output.

**Drift families:**

| family | rows | 7.94 | tree (spec) | port follows | why |
|---|---|---|---|---|---|
| IV whose first byte is NUL | 29,720 | treated as "no IV": all-zero IV, length check skipped (`3be01efb1:nse_openssl.cc:390-394`) | used; only `nil`/`""` mean absent (`nse_openssl.cc:413,416-417`) | **tree** | an upstream fix, #2640 (`3d99250c8`). `nping-brute.nse:101-103` passes 16 random bytes, so in 7.94 one run in 256 authenticates with the wrong IV |
| `openssl.nse_openssl_state` | 1 | absent | userdata whose `__gc` unloads providers (`nse_openssl.cc:606-660`) | **7.94** | nothing to unload in the port; no corpus use |
| `validity.*.year` | 2,425 certs | full year | year − 1900 (`nse_ssl_cert.cc:307-309,369`) | **7.94** | a regression in the tree: it contradicts `nmap.luadoc` ("year = 2020"), and `ssl-cert.nse:310` would print `136-10-06T…` |
| ASN.1 time strings | 13 | hand parser: raw string or an impossible table | `ASN1_TIME_to_tm` | **7.94** | the same commit, and incidental to it |
| TLS security level | 6 servers | system default, level 2 | level 0 + allow-all callback (`nsock_ssl.c:216-220`) | D3 | — |
| TLS socket I/O (EOF and close) | see below | — | — | **7.94** | output-visible: `smtp.lua:18-20` prints "connection closed" for `"EOF"` and "failed to receive data" for `"ERROR"` |
| `connect(...,"ssl")` on a UDP socket | — | TCP TLS to the same port (`3be01efb1:nse_nsock.cc:564-567`; measured: returns the certificate of a TCP server) | DTLS (`633bfe00b`) | **7.94** | the repo's Lua assumes DTLS (`comm.lua:63-67`) and runs on 7.94's C, so these paths make TCP TLS connections |
| `ecdhparams` stack use | — | `ec_curve_type` set inside each branch | set unconditionally (`nse_ssl_cert.cc:456-523`) | **7.94** | the tree can leave the stack unbalanced |
| nselib (Lua) | — | the installed copy differs | repo | repo, via `--datadir` | as in every M6 gate |

**TLS socket I/O, measured** (stable over 3 runs on 7.94):

| case | 7.94 | tree |
|---|---|---|
| plain TCP, peer closes | data, then `nil,"EOF"` | `nil,"EOF"`, then `false,"EOF"` |
| TLS, abrupt close (no close_notify) | data, then `nil,"ERROR"` | `nil,"ERROR"` on the first receive (data lost) |
| TLS, close_notify | `receive` waits the full timeout and gives `nil,"TIMEOUT"`; `receive_buf` gives `nil,"EOF"` once TCP closes, `nil,"TIMEOUT"` if TCP stays open | `false,"EOF"` |

**Rows that agree.** 212,450 rows are byte-identical across the two oracles.
The tree and 7.94 differ on 34,788 rows. 29,725 of those are stable across
two 7.94 runs, and they are the drift families above (29,721, plus 4
`bignum_rand` rows). The other 5,063 differ only through nondeterminism,
which gives ~217k agreeing rows.

**Nondeterministic rows.** Two runs of the same oracle differ on 5,068 rows.
That is a different count from the 5,063 above, which are measured against
the tree. The causes:
- GCM with no IV;
- `des3-wrap`;
- `bignum_rand`.

A tree-vs-oracle diff found 4 more `bignum_rand` rows that two runs had
missed. So the generator **tags** its nondeterministic families explicitly,
and regeneration fails on any untagged row that differs between runs.

**Error strings depend on history.**
- `NSE_SSL_LUA_ERR` reports the *oldest* queued OpenSSL error and never
  clears the queue (`nse_openssl.cc:37-38`). The bignum functions ignore
  return codes (`:89,105,127`), so their errors stay queued.
- Measured: after `bignum_div(x,0)`, the next bad-key `encrypt` reports
  "bignum routines::div by zero".
- 7.94's nsock never calls `ERR_clear_error` (the tree's `f87c5e20b` adds
  one), so TLS handshake errors can surface in `openssl.*` messages in real
  runs.
- **A drain makes the oracle exact.** Before each case, call
  `decrypt("aes-128-gcm",K16,IV12,"x")` until the message contains
  `error:00000000:`. After a drain:
  - the message is the case's own first error;
  - only 7 distinct "OpenSSL error:" strings appear across the 80,407
    `OpenSSL error:` rows.
    One of them, `error:00000000:lib(0)::reason(0)` (4,254 rows), is OpenSSL
    failing without queuing anything.
  - `Error parsing cert: %s` (`nse_ssl_cert.cc:610`) reads the same stale
    queue, so the certificate corpus is drained before each case too.

**Pinning the CI environment.** The `differential` job installs nmap with apt
on `ubuntu-latest` (`1f3184592:.github/workflows/nmap-rs-ci.yml:345-354`). The error
strings embed packed OpenSSL 3.0.13 codes. 7.94's TLS reach depends on the
compiled-in default security level, and the cipher rows depend on
`ossl-modules/legacy.so`. So the job pins its image, and the golden header
asserts:
- `nmap --version`;
- `openssl version` and `openssl version -d`;
- `OPENSSL_CONF`;
- the effective security level;
- whether the legacy provider loads.

## 4. What must be first-party whatever crates are chosen

No crate provides OpenSSL's observable behaviour. Whatever the crate
decisions, the port writes:
- **EVP name resolution:** case-insensitive, with aliases, dotted OIDs,
  provider names, and truncation at NUL.
- **EVP cipher rules:** key-length rules, IV rules, padding off by default,
  PKCS#7, and the exact error strings.
- **BN text formats:** `bn2hex` is uppercase and byte-padded; `bn2mpi`;
  `dec2bn`/`hex2bn` parse a prefix.
- **BN semantics:**
  - sign rules;
  - the silent zeros from `div` and `mod_exp`;
  - int32 truncation of `bits` and positions (`nse_openssl.cc:86-89,161,169,177`)
    and of `RAND_bytes`' length;
  - a size cap mirroring `bn_expand_internal`, past which
    `bin2bn`/`dec2bn`/`hex2bn` silently give 0 (`:62,71,80` ignore return
    codes). The exact cap must be read from `bn_lib.c` at tag
    `openssl-3.0.13`: **unverified**.
- **`BN_check_prime`'s structure** (`bn_prime.c` at `openssl-3.0.13`, `:74-98,366-371`):
  - trial division first;
  - then 64 Miller-Rabin rounds up to 2048 bits, 128 above;
  - random witnesses. Fixed bases are measurably wrong: the oracle calls
    `318665857834031151167461` composite.
- **`DES_string_to_key`**, without reading the key's `[7]`.
- **The `SSL_CERT` object's shape:**
  - it is userdata with `__name` = `SSL_CERT`;
  - `__index` reads a per-certificate attribute table cached in the
    registry, so mutations persist;
  - that table's metatable `__index` holds `digest` (`nse_ssl_cert.cc:690-722`);
  - `extensions` is absent when the certificate has none (`:225-226,599-605`);
  - name values are the raw ASN.1 string bytes. `ssl-cert.nse:216-230`
    depends on receiving raw UTF-16.
- **Key-type reporting:**
  - `type` follows `EVP_PKEY_base_id`, so RSA-PSS, SM2, DHX, X25519 and
    Ed25519 are all `unknown`;
  - `bits` follows `EVP_PKEY_bits`, for example X25519 = 253;
  - curves use OpenSSL's short names (`prime256v1`);
  - DSA's `sig_algorithm` is `dsa_with_SHA256`;
  - `ssl-enum-ciphers.nse:733` compares `pubkey.type` against the key
    exchange.
- **BER leniency and re-encoding.**
  - 7.94 accepts these framings:
    - an outer SEQUENCE with a non-minimal length;
    - an outer SEQUENCE with indefinite length;
    - a signature BIT STRING with nonzero unused bits;
    - trailing bytes.
  - `pem` and `cert:digest` are then computed over OpenSSL's *re-encoding*:
    - the outer length made minimal;
    - the tbs bytes kept as received (they are cached);
    - the unused bits masked;
    - the trailing bytes dropped.
- **OpenSSL's tables and renderers:**
  - the OID→long-name table (`obj_mac.h`: 1,251 NIDs, 671 long names);
  - the `X509V3_EXT_print` text renderers;
  - ASN1_TIME→table conversion.
- **`supported_*`**, defined by D4.

## 5. The TLS surface

**The NSE context in 7.94** (`3be01efb1:nsock/src/nsock_ssl.c`):
- `SSLv23_client_method`;
- `SSL_VERIFY_NONE` (`:180`);
- `SSL_OP_ALL`, which does not include `LEGACY_SERVER_CONNECT` on 3.0.13;
- `CIPHERS_FAST` (`:79`);
- the system security level, which is 2;
- the legacy provider loaded before `SSL_CTX_new`.

**The ClientHello it sends** (from `s_server -trace`):
- TLS 1.3 and 1.2;
- 77 suites, including 3 SEED suites, plus the renegotiation SCSV;
- no SHA-1 signature algorithms;
- groups: x25519, P-256, x448, P-521, P-384, ffdhe2048–8192.

**Other properties:**
- **No chain verification.** Expired, self-signed, MD5-signed and 512-bit
  certificates are all accepted. Every check listed in §1.3 still applies.
- **SNI** comes from `targetname`, or from the string argument itself, IP
  literals included (`nsock_core.c:377-382`).
  - A host table scanned by IP sends none; the string `"127.0.0.1"` sends
    `127.0.0.1`.
  - An empty name, or one longer than 255 characters, **aborts the whole
    nmap run** (§7, `nse-ssl-sni-fatal`).
  - rustls sends no SNI for an IP literal, and `ServerName::try_from`
    rejects names such as `"bad name x"`, which nmap sends as-is. rustls
    cannot send arbitrary SNI bytes. So the port sends no SNI in both cases,
    ledgered as `nse-tls-sni-rustls-names` and pinned per case, unless D3
    picks a first-party client.
- **Session reuse is dead in NSE.** `nu->ssl_session` is only ever NULL
  (`nse_nsock.cc:62,976`).
- **Failure looks like any other.** A failed handshake returns `nil,"ERROR"`,
  and `comm.tryssl` then retries **in plaintext**.
- **One timeout covers both steps.** The `nu->timeout` covers the TCP
  connect plus the handshake (`nse_nsock.cc:586`) and `reconnect_ssl`
  (`:479-480`).
- **close_notify costs time.** On 7.94, `recv_all` (`http.lua:517-533`)
  waits out the full socket timeout after a close_notify. The body is the
  same, but the elapsed time differs, and that interacts with
  `--script-timeout`.

**The 21-server matrix:**

| server | 7.94 | tree | rustls |
|---|---|---|---|
| TLS 1.3 (TLS 1.3-only, RSA, EC, Ed25519, expired, MD5-signed 1024-bit, BMPString) | ok | ok | ok |
| TLS 1.0-only, TLS 1.1-only | FAIL | ok | FAIL |
| TLS 1.2 RSA key exchange (AES128-SHA, AES128-GCM-SHA256) | ok | ok | FAIL |
| DHE-RSA 2048; DHE-DSS with a DSA certificate | ok | ok | FAIL |
| DHE-RSA 1024; ADH; NULL-SHA256; RSA with SHA-1-only signatures | FAIL | ok | FAIL |
| ECDHE-RSA with CBC; DHE-RSA-CAMELLIA | ok | ok | FAIL |
| P-521 only | ok | ok | FAIL (the provider has no P-521) |
| ECDHE-RSA with a 512-bit RSA certificate | ok | ok | FAIL ("InternalError"; cause not established) |

**Gaps in the matrix.**
- Every rustls success was TLS 1.3 with `TLS13_AES_256_GCM_SHA384` over
  X25519. Phase 0 has **no** fixture where rustls completes a TLS 1.2
  handshake.
- So a provider that implements only TLS 1.3, AES-256-GCM, SHA-384 and
  X25519 would pass "reaches every rustls-reachable fixture". §11 step 0
  adds the fixtures that close this gap.

**Who reaches TLS.**
- **256 scripts** reach a TLS connect: 171 only through the http family, 32
  through `comm.tryssl`/`get_banner`, and up to 30 through `reconnect_ssl`.
- **Ten scripts are unaffected by the TLS choice.** They use only `tls.lua`
  over plain sockets: ssl-enum-ciphers, ssl-dh-params, ssl-heartbleed,
  ssl-poodle, ssl-ccs-injection, sslv2, sslv2-drown, tls-alpn,
  tls-nextprotoneg and ssl-date.
- **STARTTLS servers rustls cannot reach lose their certificate.** For
  servers that support only TLS 1.2 RSA key exchange, CBC, DHE, or TLS ≤ 1.1:
  - `reconnect_ssl` fails;
  - step 3 tries TLS on the plaintext port;
  - step 4 sends a raw ClientHello without STARTTLS
    (`sslcert.lua:1060-1082`).

  All three fail, so those certificates are lost. 7.94 gets them, and the
  port today gets PEM-only results. Direct-TLS servers are still rescued by
  step 4 (`handshake_cert`, `:943-993`).

### D0 — Order relative to `nmapdb` and `lpeg`

**Options:**

### D1 — Which C is the reference

**Options:**
- (a) 7.94 everywhere;
- (b) the tree everywhere;
- (c) **Split:** the repository's C is the spec, 7.94 stays the gate's
  oracle, and the tree build arbitrates only the enumerated drift families
  in §2.

**Decided: (c).**
- **Why not (a) or (b).** (a) knowingly ships the IV bug upstream fixed.
  (b) ships the certificate-year regression and the TLS EOF data loss.
- **How (c) works.**
  - Rows that 7.94 and the tree agree on are compared against 7.94 with no
    exemption list.
  - Drift rows are **pinned, not exempted**, following the `scriptargs`
    precedent (`crates/core/tests/scriptargs_differential.rs:12-16`): each
    pin asserts the ledgered value, and the gate fails on any other
    divergence.
  - **Local regeneration.** It builds the tree (about 3 minutes) and fails
    on any 7.94-vs-tree difference outside a named family. The committed
    golden holds the full 7.94 output, plus the tree's values for the drift
    rows.
  - **CI never builds C.** This keeps the path-scoped rule (`PLAN.md:155-156`,
    LESSONS #5). The CI differential job regenerates from apt's 7.94 only,
    and requires that output to equal the committed 7.94 golden.
  - **When the drift census re-runs.** A moved oracle shows up as that
    inequality. Re-running the drift census is needed only when the
    generator or the tree's C changes, and both are local regeneration
    events.

| rustls + rustls-rustcrypto 0.0.2-alpha | no | 7 | **deny fails** (RUSTSEC-2023-0071 via `rsa`, 4 `rustls-webpki 0.102.8` advisories) |
| rustls + graviola | no (149 `asm!`) | 7 | **fails MSRV** (1.89) |
| **rustls + first-party provider** | no | 7, plus P-521 if `p521` is added | provider-less rustls is deny-clean at 1.88 with no C; **the provider itself is unmeasured** |
| first-party legacy client | no | up to 21 | all first-party gates; large (rustls is 35k lines) |
| OpenSSL by FFI behind an off-by-default feature | yes, a system library (precedent: the `pcap` feature) | oracle-exact | ASan only |

**Preliminary recommendation:** rustls with a first-party provider.
- The provider **verifies handshake signatures**:
  - RSA PKCS#1 v1.5 and PSS, written first-party over num-bigint (public
    data only);
  - ECDSA P-256/P-384, and P-521 if `p521` is added, with RustCrypto;
  - Ed25519 with the dalek crate already in the tree;
  - Ed448 is not offered, which is ledgered.
- **Certificates:**
  - it parses the leaf with `d2i_X509`'s acceptance rules plus the
    exact-length check;
  - it rejects the key types OpenSSL's TLS rejects (DH, X25519, unknown
    OIDs) and a key type that does not match the suite;
  - it requires RFC 5746.
- **ClientHello order:** suites, signature algorithms and groups follow
  7.94's ClientHello wherever rustls has them, and every other ClientHello
  difference is ledgered.
- **Legacy reach** goes to `nse-tls-modern-only`, retired by **M6.7, legacy
  TLS**, which gets its own Phase 0 (LESSONS #031).
  - Its fixtures are pinned **in both directions**: servers 7.94 reaches and
    the port does not, and the reverse.
  - It also records what registration (g) takes away. Legacy *STARTTLS*
    servers return a PEM-only result today but nothing after g, because
    sslcert then trusts `reconnect_ssl` (§5).

The final choice waits for the spike's measured provider size, crate union
and unsafe count.

### D4 — Which algorithms are offered, and what `supported_*` reports

**Options:**
- (a) full parity: 21 digests and 170 cipher names. This includes constructs
  that are broken in C: GCM encrypt returns no tag, GCM decrypt always
  fails, and CCM/OCB/XTS fail.
- (b) **the corpus set plus its family closure:**
  - digests md4, md5, sha1, ripemd160, sha224/256/384/512, sha512-224/256;
  - ciphers des-ecb, des-cbc (alias `des`), aes-128/192/256 in ecb and cbc,
    cast5-ecb and cast5-cbc;
  - each with OpenSSL's aliases, OIDs, case-insensitivity and NUL
    truncation.
- (c) (b) plus whatever a crate makes cheap.

**Decided: (b).**
- There are 0 corpus uses outside it, and every algorithm offered is a gate
  obligation.
- Weak algorithms are offered, because smbauth, mssql, vnc, afp, rsync, tns
  and sasl cannot authenticate without them.
- `supported_*` returns exactly what is accepted, sorted with `strcmp`.
  - The C's lists do not reflect availability either: they stay at 56 and
    170 entries with the legacy provider unloadable.
- Oracle-accepted names outside (b) become one generated pin family,
  `Unknown digest/cipher algorithm: <name>`, ledgered as
  `openssl-algorithm-subset`.

### D10 — TLS placement and `-sV` SSL tunnels

**The second consumer.** `-sV` already defers SSL/STARTTLS tunnels "until
rustls" (`servicescan-connect-only`; `ssl_tunnel: false` at
`sys/src/servicescan.rs:8,180`).

**Recommendation:**
- the client lives in a shared `sys::tls`, not inside `sys::nsenet`;
- `-sV` tunnels are a follow-on step once NSE TLS is gated, not part of
  M6.5.

### D11 — Licence of OpenSSL-derived data

**The question.** M6.5e commits two kinds of data generated from OpenSSL 3
(Apache-2.0):
- the OID→long-name table;
- the `X509V3_EXT_print` formats.

This crate is `MIT OR Apache-2.0` (`Cargo.toml:27`).

**Recommendation:** generate the table at build-check time from OpenSSL's
`objects.txt`, and commit it with an Apache-2.0 NOTICE. This needs your
sign-off before M6.5e.

The larger question is project-wide and predates M6.5: the port translates
NPSL-licensed C (`nse_ssl_cert.cc:9-17`). It is not M6.5's to settle.

## 10. Engineering choices made (recorded; you may veto)

- **E1 (was D5) — primitives.**
  - **Crates:** RustCrypto md4, md-5, sha1, ripemd, des, aes and cast5, on
    the digest 0.10 / cipher 0.4 generation already locked:
    - +17 crates, deny and MSRV clean;
    - 0.11 would add +7 duplicates and fails MSRV.
  - **First-party:** ECB/CBC modes and padding, HMAC (RFC 2104, about 30
    lines), the EVP rules and `DES_string_to_key`.
  - **Precedent:** SHA-256 went in-tree because a hash is exhaustively
    testable (`sigstore-sha256-in-tree`). Ed25519 went to a crate because
    its semantics are contested (`sigstore-ed25519-dependency`).
  - The registry unsafe count (aes 63 blocks) is ledgered as ed25519-dalek's
    was.
- **E2 (was D6) — bignum.**
  - num-bigint 0.4 without `rand`: +3 crates, deny and MSRV clean.
  - A first-party BN layer owns the semantics in §4. It guards num-bigint's
    3 measured panics: division by 0, `modpow` with m = 0, and a negative
    exponent.
  - The operand-size cap comes from the step-0 spike.
- **E3 (was D7) — randomness.**
  - `getrandom` (0 new crates) behind one seam serves:
    - `rand_*` and `bignum_*rand`;
    - the MR witnesses;
    - the TLS provider.
  - The seam can be seeded only under `cfg(test)`.
  - Gates:
    - lengths and ranges;
    - **non-constancy**: two 32-byte draws differ, and no 1 MB draw is all
      one byte;
    - a release-build check that the seam is the OS CSPRNG.
- **E4 (was D8) — error text.**
  - Byte-exact for the failing call's own first error. The justification is
    per module, as for patterns (DIVERGENCES.md, "Lua patterns"): scripts print
    these messages.
  - Argument errors follow the existing `*-bad-argument-naming` pin family,
    covering `'openssl.bignum_mod_exp'`, `'?'` under `pcall`, and
    `calling 'get_ssl_certificate' on bad self`.
  - Staleness, including staleness across modules, is ledgered as not
    reproduced.
- **E5 (was D9) — X.509.**
  - A one-day spike of `x509-cert` over the corpus *with its BER family*.
    It becomes the parser only if it agrees on every accept/reject verdict
    and the re-encoding.
  - The BER leniency makes failure likely, in which case the reader is
    first-party.
- **E6 — memory.**
  - M6.5 routes every size through `stdlib::reserve` and records userdata
    bytes.
  - The CLI's `memory_limit: None` is left as it is, and is now ledgered as
    `nse-cli-no-memory-budget`.
    - nmap has no budget either, but its Lua allocator turns a refused
      allocation into a catchable error. Here, a refused allocation outside
      `try_reserve` aborts.
    - A default budget is a user-visible change, left to M7.
- **E7 — crates and the piccolo precedent.**
  - Under D2(D), the crypto code (b–e) lands before registration (g), which
    sets aside "a dependency must be earned by shipped code"
    (`crates/core/Cargo.toml:46-50`) for one milestone. This is stated, not
    hidden.
  - A test asserts that `openssl` cannot be required in a release build
    before g.

## 14. Step 0: the spikes, and what they decided

Three spikes, as §11 step 0 asked, each scratch code outside the workspace
(`spikes/m65-tls-provider`, `spikes/m65-x509`, `spikes/m65-bignum`), each
measured against the C: nmap 7.94 and OpenSSL 3.0.13 on this machine. They
decide D3 and E5, set the bignum cap, and record D10 and D11 as approved.

### 14.1 The D3 spike: rustls with a first-party provider

**What was built.** A rustls 0.23.46 `CryptoProvider` over RustCrypto
primitives of the digest-0.10 / cipher-0.4 generation the tree already locks
through ed25519-dalek, so no second version of `digest`, `sha2`, `subtle` or
`generic-array` enters: AES-GCM and ChaCha20-Poly1305 for TLS 1.3 and TLS 1.2
(`aes-gcm`, `chacha20poly1305`), SHA-256/384 and HMAC (`sha2`, `hmac`), the
TLS 1.2 PRF and TLS 1.3 HKDF through rustls's own `PrfUsingHmac` and
`HkdfUsingHmac`, X25519 (`x25519-dalek`) and P-256/P-384/P-521 (`p256`,
`p384`, `p521`) key exchange, and signature verification: ECDSA on the three
curves, Ed25519 with `verify_strict` only (LESSONS #037), and RSA PKCS#1 v1.5
and PSS **first-party over `num-bigint`** (221 lines; the `rsa` crate carries
RUSTSEC-2023-0071 and fails `cargo deny`). No FFDHE: it would need
secret-dependent bignum arithmetic (§6). The `randomness` is `getrandom`
behind one seam (E3).

Over it, a verifier that applies nmap's rules rather than webpki's (§1.3): no
chain verification, but every certificate entry parsed by a first-party DER
walker with an exact length (`statem_clnt.c:1808-1811,1813-1816`), a key
present and of a type OpenSSL's TLS accepts (`:1903,1909`), the key matching the signature
scheme (`:1918-1922`), and the ServerKeyExchange or CertificateVerify
signature verified (`:2302-2306`, `statem_lib.c:532-538`). The ClientHello
lists suites, groups and signature algorithms in 7.94's order restricted to
what rustls carries (`fixtures/clienthello_suites_794.txt`, from the
`s_server -trace` of §5),
with one deliberate change: the ECDHE-RSA suites go before the ECDHE-ECDSA
ones at each strength, because 7.94 offers DHE-RSA before any ECDHE suite and
so gets the RSA certificate from a dual-certificate server honouring client
preference, and `ssl-cert` prints that certificate.

**The fixture run** (`spikes/m65-tls-provider/fixtures/run.py`, results in
`fixtures/results/results.md`): 61 fixtures on loopback, each served to nmap
7.94 (through `s0probe.nse`: `connect(...,"ssl")`, or SMTP then
`reconnect_ssl`, reporting the leaf's SHA-256) and then to the spike's
`tlsprobe`. The servers: `openssl s_server` 3.0.13 with each suite, group and
signature scheme forced; dual certificates in the three variants; STARTTLS
through a small SMTP front over Python's `ssl` (OpenSSL 3's `s_server` has no
`-starttls`); weak and odd certificates; chains of 70,606 and 104,267 bytes;
SNI shapes; the legacy set; a fake TLS 1.2 server that sends ServerHello,

### 14.3 The bignum spike: the operand caps

(`spikes/m65-bignum/RESULT.md`: a Xeon at 2.10 GHz, gcc 13.3, OpenSSL
3.0.13, rustc 1.88 release, `num-bigint` 0.4.8; medians of three; each
measurement capped at 120 s, past which a figure is extrapolated on the
fitted exponent and marked so.) The sizes are the peer-chosen ones of §6:
a TLS DH `p` arrives through a 2-byte length, at most 524,280 bits; an ssh2
group-exchange `p` through a 4-byte one with no check; and scripts then
call `mod_exp`, `is_safe_prime` and `todec`/`dec2bn` on them.

| milliseconds, C / Rust | 8,192 bits | 16,384 | 65,536 | 524,280 | 1,048,576 | 8,388,608 |
|---|---|---|---|---|---|---|
| `mod_exp`, N-bit exponent (one Miller-Rabin round) | 119 / 334 | 966 / 2,153 | 96,448 / >120 s (~91 s) | >120 s both (~14–26 h / ~7 h) | — | — |
| `mod_exp`, 2,048-bit exponent (the DH shape) | 30 / 69 | 121 / 264 | 3,070 / 4,288 | >120 s both (~200–390 s / ~274 s) | — | — |
| `mod_exp`, e = 65537 | 0.37 / 2.66 | — | 26.9 / 192 | 1,777 / 12,270 | 6,637 / 42,706 | >300 s / ~52 min |
| `bn2dec` | — | — | — | 232 / 19 | 944 / 49 | 60,009 / 1,146 |
| `dec2bn` | — | — | — | 26 / — | 103 / — | 6,705 / 6,563 |
| trial division (`is_prime`'s floor) | 3.2 / 1.4 | — | — | 216 / 93 | 433 / 186 | 3,504 / 1,507 |

`is_prime` is `BN_check_prime`: trial division (`bn_prime.c:74-85`), then
64 Miller-Rabin rounds up to 2,048 bits and 128 above (`:94-99`), each
round one full-exponent `mod_exp`. The typical input stops at trial
division, which is linear (Rust 0.43× of C); about 11.5 % of random odd
inputs survive it and pay one round. The worst case is a prime: measured
on a real 4,096-bit prime, 1,966 ms in C and 6,973 ms in Rust (the
derivation 128 × one round agrees within 3 %); derived from there, 15.3 s
/ 42.7 s at 8,192 bits, 124 s / 276 s at 16,384, about 3.4 h / 3.2 h at
65,536, and `is_safe_prime` twice each (31 s / 85 s at 8,192; 247 s /
551 s at 16,384). Peak RSS at 8,388,608 bits is 12 MB in C and 20 MB in
Rust: memory is not the limiting resource, time is.

**The cap, confirmed.** `bn_expand_internal` refuses more than
`INT_MAX / (4 * BN_BITS2)` words (`bn_lib.c:270`): in C, `BN_bin2bn` of
67,108,856 bytes succeeds and of 67,108,857 fails with
`bignum routines::bignum too long`, leaving the number 0; through nmap
7.94, `bignum_bin2bn(string.rep("\xff", 67108857))` prints `0` with no
error (1.96 s, rc 0), one byte fewer prints 134,217,712 hex digits.
`num-bigint` 0.4.8 panics on four inputs, each confirmed under
`catch_unwind`: division by zero, remainder by zero, `modpow` with a zero
modulus, and `BigInt::modpow` with a negative exponent, invertible base or
not (E2 counted three); the port's BN layer pre-checks all four.

**The caps.** Mirroring OpenSSL's 536,870,848-bit cap and relying on
pre-emption (§6) is not viable: `modpow` is one native call with no
cancellation point, so the watchdog could only notice after 600 s and
never unwind it, and at that cap `mod_exp` with e = 65537 is about 19
days in C, `bn2dec` about 3 days, one Miller-Rabin round years. The port
takes per-operation caps instead, each leaving a single call under the
10-minute watchdog with about five times to spare, measured on the slower
implementation:

- `is_prime` and `is_safe_prime`: **8,192 bits** (worst 85 s in Rust,
  31 s in C; 16,384 would be 551 s). That is the largest standardised
  group, RFC 7919's ffdhe8192 and ssh2's group-exchange maximum. The
  Miller-Rabin loop is first-party and yields between rounds, so the
  watchdog can stop it.
- `mod_exp`: **every operand at most 16,384 bits** (worst 2.2 s / 1.0 s
  with a full-size exponent). It cannot be interrupted, which is why its
  cap sits lowest against its cost.
- Construction and the linear operations (`bin2bn`, `dec2bn`, `hex2bn`,
  `bn2dec`, `bn2hex`, `bn2bin`, `add`, `div`, `num_bits`, the bit
  operations): **1,048,576 bits** (`bn2dec` 49 ms in Rust, RSS under
  20 MB), twice the TLS 2-byte maximum, so whatever a TLS peer sends
  still converts.
- Over a cap, the call raises the memory budget's refusal
  (`stdlib::reserve`, §6), not 7.94's silent zero: a zero would flow into
  `mod_exp` or `div` as a zero modulus, the panic above.

Ledgered as `nse-bignum-operand-cap`: 7.94 computes up to its own cap,
for minutes to days, and returns 0 silently above it. What differs in
practice: `ssl-dh-params`'s `is_safe_prime` on a DH group over 8,192 bits
(7.94 answers after about four minutes at 16,384), ssh2's `mod_exp` on an
exchange whose `p` exceeds 16,384 bits, and conversions past 1,048,576
bits; no standardised group produces any of them. Not measured, and
extrapolated as marked: full-exponent `mod_exp` above 65,536 bits, the DH
shape at 524,280 and above, e = 65537 at 8,388,608 bits in Rust; and
`BN_check_prime` on a real 8,192-bit prime, whose generation did not
finish in 120 s (the derivation is backed by the 4,096-bit check).

### 14.6 Step a: the oracle, and what it found

Step a is committed in `tests/differential/m6/`. Its README section, "M6.5
step a — the `openssl` corpus", describes each file. The corpus has 29,476
cases: 7.94's golden, this tree's C built standalone as the spec (D1), and
3,208 drift rows, each in a §2 family (`year` 2,546, `ivnul` 648,
`asn1time` 13, `state` 1). It also commits the TLS fixtures of 14.1 with
7.94's result on each, and the C ban of §6. Building the oracle found the
following:

- **The wrong-length IV is reached far more widely than eight rows.** Any
  IV given to a cipher without one, and any IV one byte long or short,
  reaches `nse-openssl-iv-length-uaf`: 1,688 rows. Before the rows were
  tagged, the first 7.94 run crashed more than 1,000 times. The rows are
  now tagged `ub:` and never run as written. Their golden is the message
  the C means, from one named repair of the oracle, and the generator
  checks the tag against the rows that raise it.
- **RC4 with an empty key reads past the key** (`nse-openssl-rc4-empty-key`):
  the §12 inference, now measured. The sanitizer screen cannot see it,
  because libcrypto is not instrumented. Two 7.94 runs disagreeing on an
  untagged row is what caught it.
- **Three kinds of nondeterminism in 7.94 itself**, each tagged and
  compared by shape:
  - the random functions;
  - GCM and 3DES key wrap with no IV, where libcrypto draws one;
  - the name an argument error gives `bignum_rand`/`bignum_pseudo_rand`,
    one function under two names, ordered by Lua's hash seed
    (`nse-openssl-rand-alias-name`).
- **`supported_ciphers` is empty** unless nsock's SSL initialisation has
  run. OpenSSL 3 lists only registered names, and `luaopen_nsock`
  registers them. The oracle replays it.
- **The C sabotage measured the corpus**: 34 variants, all caught. The first
  pass missed four: the random bignums' top bit; a message over 1,000 bytes;
  and two mutations of `time_to_tm`'s own parser, which OpenSSL 3 builds do
  not compile. The corpus gained the first two; the last two were replaced.
- **Independent references agree** with every golden row they can compute:
  Python ints, CPython's non-OpenSSL hashes, and nettle for md4, ripemd160,
  sha512-224/256 and sm3. whirlpool has none.
