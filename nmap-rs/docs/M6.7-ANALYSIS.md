# M6.7 — Legacy TLS: Phase 0

M6.5 shipped NSE's TLS client as rustls 0.23.46 over a first-party provider
(D3), with "legacy reach" left to `nse-tls-modern-only`, "retired by M6.7,
legacy TLS, which gets its own Phase 0 (LESSONS #031)"
(`docs/M6.5-ANALYSIS.md` D3). This is that Phase 0. No port code is written
before the decisions in §9 are made.

Everything measured here is against the oracle's pinned environment: nmap
7.94 linked to OpenSSL 3.0.13 at security level 2 (`m65_tls_golden.txt`'s
header). The measurement is `spikes/m67-legacy-tls/reach.py` (§13).

## 0. Value: what M6.7 changes

- **Every TLS socket a script opens**: `connect(..., "ssl")`,
  `reconnect_ssl` and `comm.tryssl` (M6.5's census: 212 scripts, 44 of them
  `default`). Against a server that speaks only what the port lacks, they
  fail with `nil, "ERROR"` where 7.94 gets through.
- **The STARTTLS regression step g took on purpose.** With `openssl`
  registered, sslcert reads a STARTTLS certificate by `reconnect_ssl`, so a
  mail, IMAP, POP3, FTP or LDAP server with only legacy suites gives
  ssl-cert nothing. Before step g it gave a PEM-only certificate
  (`nse-tls-modern-only`, CLI scenario `starttls-legacy`).
- **What it does not change:** ssl-enum-ciphers, sslv2 and the other
  scripts that speak TLS through `tls.lua` build their records in Lua and
  never touch the client.

**Not measured: how many servers on real networks are reachable only by
what the port lacks.** No public scan dataset is reachable from this
environment. The families below are what OpenSSL-based and embedded
servers fall back to (RSA key exchange and CBC on older appliances,
management controllers and printers; DHE with the server's own parameters
on older mail servers), which is where nmap is used. The decision in §9
should not rest on a prevalence figure this document does not have.

## 1. The gap, measured

7.94 offers 78 suites plus `TLS_EMPTY_RENEGOTIATION_INFO_SCSV`
(`m65_tls/clienthello_suites_794.txt`). The port offers 9: TLS 1.3's three,
and ECDHE with AES-GCM and ChaCha20-Poly1305 for RSA and ECDSA.

Where neither reaches (out of scope, recorded): DHE with a 1,024-bit group
(security level 2 refuses it in 7.94), TLS 1.0 and 1.1 (refused by 7.94 at

**The same limits behind four more step-f1 pins**, all in the TLS client:
- `nse-tls-handshake-64k`: rustls refuses a handshake message over 65,535
  bytes; OpenSSL allows a certificate list up to 102,400
  (`chain-over64k`, `chain13-over64k`, `cert-chain-over64k`);
- `nse-tls-no-reneg-info-accepted`: rustls goes on without
  `renegotiation_info`, where 7.94 aborts with alert 40 (`fake-noreneg`,
  `cert-fake-noreneg`): a difference in the other direction;
- `nse-tls-alert-numbers`: alerts rustls cannot send from a verifier, 50
  and 80 (`fake-trail`, `fake-unknownoid-cert` and their `cert-*` rows);
- `nse-tls-sni-rustls-names`: no `server_name` for an IP literal or a name
  rustls will not encode, and a trailing dot dropped (`sni-*`, `udp-ssl`).

## 2. Why rustls cannot reach them today (by reading 0.23.46)

- **RSA key exchange:** `KeyExchangeAlgorithm` has `DHE` and `ECDHE` only
  (`msgs/handshake.rs:1900-1907`). There is no hook for a client that
  encrypts a premaster secret to the server's key.
- **CBC record protection:** a provider's TLS 1.2 record layer is
  `Tls12AeadAlgorithm`, whose `KeyBlockShape` has an encryption key, a fixed
  IV and an explicit nonce (`crypto/cipher.rs:72-94`), and no MAC key. The
  key block can be split so that the "keys" are the MAC keys, but an
  `AeadKey` holds at most 32 bytes and SHA-384's HMAC key is 48: CBC with
  SHA-1 and SHA-256 fits by contortion, CBC-SHA384 does not.
  `encrypt_then_mac` (RFC 7366), which 7.94 offers, cannot be negotiated.
- **DHE with the server's own group:** the client looks the server's `p`
  and `g` up among the provider's groups by value
  (`client/tls12.rs:955-964`), so only the RFC 7919 groups a provider
  supplies can match; any other group ends the handshake with
  `IllegalParameter`.
- **DSA:** no `SignatureScheme` maps to `SignatureAlgorithm::DSA`, and the
  TLS 1.3 rules outlaw it outright (`enums.rs:575-578`).
- **The limits:** `MAX_HANDSHAKE_SIZE` is `0xffff`
  (`msgs/deframer/handshake.rs:376`); `renegotiation_info` is merely
  allowed unsolicited (`client/hs.rs:747`), never required; a verifier's
  error maps to a fixed set of alerts.

## 3. What a provider can add without changing rustls

These go through rustls's public provider interface, as step f1's provider
does now:
- **AES-CCM and AES-CCM-8** for ECDHE (and DHE, below) in TLS 1.2: an AEAD
  (RustCrypto `ccm` 0.6);
- **ARIA-GCM** for ECDHE and DHE: an AEAD (`aria` 0.2 under the `aes-gcm`
  crate's generic GCM);
- **DHE with the RFC 7919 groups**, TLS 1.2 AES-GCM, ChaCha20 and the AEADs
  above: a key-exchange group whose `ffdhe_group()` names the group, with
  the arithmetic over `num-bigint` (already in the tree);
- **TLS 1.3 key shares** ffdhe2048 to ffdhe8192 (the same arithmetic) and
  X448 (`x448`, published only as 0.14.0-pre.12; or first-party).

That is **9 of the 22 rows**, and the `tls13-x448` and `tls13-ffdhe2048`
pins of step f1. It touches no rustls code, so it has none of option (b)'s
maintenance cost.

## 4. What needs rustls itself to change

**13 rows**, and the four pins of §1:
- RSA key exchange (7 rows): a `KeyExchangeAlgorithm::RSA`, the premaster
  secret (two version bytes and 46 random ones) encrypted with PKCS#1 v1.5
  to the leaf's key, and no ServerKeyExchange;
- CBC with MAC-then-encrypt, and encrypt-then-MAC when the server agrees
  (4 rows beyond RSA key exchange's: ECDHE three, DHE one; with Camellia and
  SEED as block ciphers): a record layer beside the AEAD one, with MAC keys
  of any size;
- DHE with the server's own group (1 row): a key exchange made from the
  ServerKeyExchange's `p` and `g`, checked as OpenSSL checks them (at least
  2,048 bits at security level 2; `g` in range; `p` within OpenSSL's
  10,000-bit maximum);
- DSA certificates (1 row): `dsa_sha1`/`dsa_sha224`/`dsa_sha256` in TLS 1.2,
  verified first-party or with RustCrypto's `dsa` 0.7;
- the four limits: the handshake message size (102,400, as OpenSSL),
  `renegotiation_info` required (RFC 5746, as 7.94), the two alert numbers,
  and the server names.

## 5. The options for §4

| option | reach (22) | also retires | ships C | size | maintenance |
|---|---|---|---|---|---|
| (a) provider only (§3), the rest stays ledgered | 9 | 2 pins | no | small | none beyond the provider |
| (b) **rustls vendored and patched**, as piccolo is (`crates/vendor/piccolo`, patches `0001`-`0013`) | 22 | the four entries of §1 | no | the patches (by reading, a few hundred lines in `client/tls12.rs`, `tls12/`, the deframer and `enums.rs`) | every rustls security release re-applied; the patch set is the diff to audit |

| (d) rustls first, a first-party legacy client on failure | 22 | some | no | as (c) | as (c) |
| (e) OpenSSL by FFI behind an off-by-default feature | 22 | all, exactly | **yes** | small | conflicts with the C ban (`deny.toml`, M6.5 §6) |

**What weighs most against (c) and (d):** 7.94 sends one ClientHello that
offers all 78 suites, both versions at once, and the server picks. A second
client cannot share that hello: (c) would have to send TLS 1.2 and 1.3 from
one stack anyway, which is (b)'s work done twice; (d) makes a second
connection where 7.94 makes one, which a server, an IDS or a rate limiter
sees, and doubles the time against a silent server.

**What weighs against (b):** vendoring a security-critical crate means
watching its advisories and re-applying the patches on every release, and
the patches are code no upstream reviews. The piccolo precedent shows the
process works here (PROVENANCE.md, a patch series, a test that the vendored
tree is the upstream release plus exactly those patches).

## 6. Threat model (extends THREAT-MODEL.md §8)

The new code parses what the server sends, as the current client does; the
server is the attacker.
- **CBC padding and MAC checks.** A padding-oracle or Lucky-13 attack would
  need the attacker to watch the client's own decryption failures for
  records it chose. Here the attacker is the server, which holds the keys
  already. Constant-time checks are still the default, as the record layer
  is shared with servers the scan did not choose.
- **The server's own DH group:** a group of 10,000 bits costs the client one
  modular exponentiation of that size per handshake. OpenSSL caps it there;
  the port caps it there too, and the cost goes into the fuzz targets'
  budgets. A small subgroup or `g` out of range is refused as OpenSSL
  refuses it.
- **RSA key exchange:** the premaster comes from the one randomness seam
  (E3); nothing in it depends on server data.
- **The 102,400-byte handshake limit** is OpenSSL's; buffering is bounded
  by it.

## 7. The oracle

The M6.5 fixture gate (`gen_m65_tls.py`, 107 rows) runs both programs
against the same servers and compares results and what the server saw.
M6.7 adds the 22 rows of §1 (and the out-of-scope ones as rows that must
fail on both sides), and the ClientHello itself: the suites, groups and
signature algorithms the port offers, in order, against
`clienthello_suites_794.txt`. Every pin of §1 then turns into an `agree`
row or stays a named pin.

The oracle is pinned to OpenSSL 3.0.13 at security level 2. An nmap built
against an OpenSSL at level 1 also reaches TLS 1.0 and 1.1 and 1,024-bit
DHE; the port follows the pinned oracle, and the ledger says so.

## 8. Where the evidence disagreed, and what won

- **"DHE is supported" (rustls's `KeyExchangeAlgorithm::DHE`) against the
  row `dhe-rsa-gcm-own2048`.** rustls supports DHE for RFC 7919 groups only;
  the fixture of step a (`tls12-dhe2048`, `-dhparam dh2048.pem`) is the
  server's own group. Measured: the RFC 7919 rows are provider work, the
  own-group row is not.
- **CBC "fits" `KeyBlockShape`.** It fits for SHA-1 and SHA-256 MACs by
  splitting the key block against its labels, and not for SHA-384; and
  encrypt-then-MAC cannot be negotiated without rustls knowing about it. A
  record layer that only works by mislabelling is the kind of patch (b)
  would carry anyway, under its own name.

## 9. Decisions

**Decided (2026-10-31): D1 (a) then (b), D2 (a), D3 (a), D4 (b), as
recommended.** Step 0 (§11) follows.

### D1 — How far M6.7 goes, and how

- (a) provider only: 9 of 22 rows, two pins retired, no rustls change.
- (b) **rustls vendored and patched**: 22 of 22, and the four entries of §1.
- (c), (d), (e) as in §5.

**Decided: (a) first, then (b).** (a) is risk-free and reaches the
TLS 1.3 groups and the RFC 7919 servers within weeks; (b) is the only option
that keeps 7.94's single ClientHello while reaching RSA key exchange and CBC.
Doing (a) first also makes (b)'s patch set smaller: it then holds only what
a provider cannot express.

### D2 — Which ciphers

- (a) **all 78 of 7.94's suites**, Camellia, ARIA and SEED included (SEED
  has no RustCrypto crate: first-party, about 200 lines with its RFC 4269
  vectors);
- (b) AES and ChaCha20 only, the rest ledgered as `openssl-algorithm-subset`
  is for NSE's `openssl` module.

**Decided: (a).** A server that negotiated Camellia or SEED did so
because nothing else was on offer; dropping them reintroduces the gap this
milestone closes, and each is small and has published vectors.

### D3 — The ClientHello

- (a) **7.94's: the same suites in the same order, the same groups and
  signature algorithms, `encrypt_then_mac`, `extended_master_secret`, the
  renegotiation SCSV**, each difference that remains ledgered;
- (b) only what the port can carry, in its own order.

**Decided: (a).** A server with client preference picks by the
client's order (`dual-tls12-clientpref` already differs for this reason),
and what the server sees is part of the gate.

### D4 — X448

- (a) `x448` 0.14.0-pre.12, a pre-release;
- (b) **first-party over `num-bigint`**, with RFC 7748's vectors;
- (c) not offered, ledgered.

**Decided: (b)**, unless a stable `x448` is published before step a:
a pre-release in the TLS path is a supply-chain exception, and RFC 7748's
ladder is short.

*Amended by step a (§15):* the ladder is over `crypto-bigint`, not
`num-bigint`. M6.5's threat model forbids secret-dependent work over
`num-bigint` in the provider (docs/M6.5-ANALYSIS.md, "Hard rule"), and the
X448 scalar is a secret. `crypto-bigint` 0.7.10 was already in the tree,
through the NIST curves, and is constant time. The same applies to FFDHE.

## 10. Engineering choices made (recorded; you may veto)

- `sys::tls` stays `forbid(unsafe_code)`; the new crates are RustCrypto's
  `ccm`, `aria`, `camellia` and `cbc`, measured by step 0 (§14). DSA is
  first-party over `num-bigint`, as RSA verification already is: the `dsa`
  crate was measured and brings `num-bigint-dig` with a build script and
  `unsafe`, and older copies of five crates the tree already has (§14).
- The vendored rustls (D1 (b)) follows piccolo's layout: the upstream
  release unpacked, a numbered patch series, `PROVENANCE.md`, and a test
  that the tree equals the release plus exactly those patches.
- The handshake size limit is OpenSSL's 102,400 bytes, not a new number.

## 12. Not verified

- How common the legacy-only server families are on real networks (§0).
- The size of (b)'s whole patch set. Step 0 measured the RSA key-exchange
  patch and proved it end to end (§14). The other four are estimated by
  reading.
- That rustls's `Tls12AeadAlgorithm` carries CCM-8's 8-byte tag and ARIA's
  GCM without a patch (by reading, yes; step a confirms).

about 4 ms per operation in release. It is not constant-time: the ephemeral
scalar is the only secret, and step a decides whether a fixed-limb field
replaces it before it ships.

(D3 (a)) is therefore a rustls patch, not a provider setting.

**The RSA key-exchange patch, proven.** `spikes/m67-legacy-tls/rustls-0.23.46-rsa-kx.patch`

- `KeyExchangeAlgorithm::RSA`.
- `CryptoProvider::rsa_key_transport`: an optional `RsaKeyTransport` hook that
  encrypts the premaster to the leaf. `fips()` is false when it is set, and
  the builder takes it as a key exchange for its "suite has a group" check.
- The client skips the ServerKeyExchange and its signature.
- The client makes the premaster (0x0303 and 46 random bytes), sends the
  ClientKeyExchange with a u16 length, and derives the secrets through a new
  `ConnectionSecrets::from_premaster`, with the same PRF and EMS.
- Exhaustive matches on the server side get an arm. The server never selects
  an RSA suite, because its filter asks for ECDHE or DHE.

`spikes/m67-legacy-tls/provider-rsa-kx.patch` is the port's side, 2 files
(+86 −1): RSAES-PKCS1-v1_5 in `sys::tls::rsa`, the hook reading the leaf
through the verifier's reader, and `TLS_RSA_WITH_AES_{128,256}_GCM`.

## 15. Step a: the provider (results)

**What was built** (`crates/sys/src/tls/`):

- **AEADs.**
  - The TLS 1.2 explicit-nonce AEAD (`aead::Aead12`, formerly `Gcm12`) is now
    generic over tag length. One record format covers AES-GCM, ARIA-GCM (RFC
    6209; `aria` under `aes-gcm`'s generic GCM), and AES-CCM and AES-CCM-8
    (RFC 6655, 7251; `ccm` over `aes`): a 4-byte salt, an 8-byte explicit
    nonce, and a 16- or 8-byte tag.
  - The new crates are `ccm` 0.5.0 and `aria` 0.1.0, which step 0 measured.
    `aes` 0.8 was already in the tree.
- **Key exchange** (`kx.rs`, `x448.rs`):
  - **X448:** RFC 7748's ladder over `crypto-bigint`'s fixed 448-bit
    Montgomery form. The swap is a constant-time `ct_assign` and the
    inversion is constant time. An all-zero result (a low-order point) is
    refused.
  - **The five RFC 7919 groups**, for TLS 1.2 DHE and TLS 1.3 key shares:
    - **Exponentiation:** `BoxedMontyForm::pow_bounded_exp`, constant time
      for a given exponent length.
    - **Exponent length:** OpenSSL's for named groups, 225, 275, 325, 375 and
      400 bits. It is public.
    - **Checks on the peer's value:** 1 < y < p − 1 and no longer than p. TLS
      1.3 also requires exactly p's length.
    - **Secret:** padded to p's length in TLS 1.3; in TLS 1.2 its leading
      zeros are removed.
  - Neither touches `num-bigint` (§9, D4 amended).
- **Suites:** the TLS 1.3 three, then 23 TLS 1.2 suites, in 7.94's order:
  ECDHE-RSA, ECDHE-ECDSA and DHE-RSA, each with AES-GCM, ChaCha20, AES-CCM,
  AES-CCM-8 and ARIA-GCM, as 7.94 offers them. The one exception is M6.5's:
  each ECDHE-ECDSA suite comes after the ECDHE-RSA suite that follows it.
  DHE-DSS waits for DSA (step e).
- **Groups,** in 7.94's order: x25519, P-256, X448, P-521, P-384, then
  ffdhe2048 to ffdhe8192. The key share is x25519's, as before.

**Gates:**

- **TLS fixture gate:** 126 rows (one new, below). `--check-port` gives
  **90 agree, 36 pinned, 0 bad** (it was 81 and 44).
  - **Now agree:** `tls13-x448`, `tls13-ffdhe2048`, `legacy-tls13-ffdhe4096`,
    `legacy-ecdhe-rsa-aria128-gcm`, `legacy-ecdhe-ecdsa-aes128-ccm` and
    `-ccm8`, and `legacy-dhe-rsa-gcm-ffdhe2048`, `-ffdhe3072` and
    `legacy-dhe-rsa-chacha-ffdhe2048`. These have the same leaf, version,
    suite, group and signature algorithm as 7.94.
  - **Repinned to the new `nse-tls-dhe-own-group`:** `tls12-dhe2048` and
    `legacy-dhe-rsa-gcm-own1024`. Both now negotiate DHE, and the port refuses
    the server's group with alert 47.
- **M6.4 CLI scenarios:** 0 of 24 differ.

**Unit tests:**

- X448 passes RFC 7748 §5.2's two vectors, the iterated vector (1 and 1,000
  iterations) and §6.2's exchange. A low-order point gives zero.
- **AEAD known answers.** OpenSSL 3.0.13's libcrypto (EVP) computed them for
  AES-128/256-CCM, -CCM-8 and ARIA-128/256-GCM. The AES-128-CCM ciphertext
  also matches NIST SP 800-38C example 3. A flipped tag bit is refused.
- **CCM-8 record framing:** a record round-trips at 8 + n + 8 bytes, and
  every record shorter than 16 bytes is a decrypt error.
- **FFDHE:**
  - ffdhe2048 and 3072 agree with `num-bigint`'s modpow, an independent
    implementation run on public test values.
  - Out-of-range and wrongly sized shares are refused.
  - The TLS 1.2 secret loses its leading zero byte. The test searches for an
    exponent whose secret starts with one.
- **ClientHello:** the suites and the groups match their 7.94 lists.
- **Miri:** the TLS tests are clean (16 run, 15 ignored for speed). Under
  Miri a ladder or a 2,048-bit exponentiation takes minutes.

**Fuzz:**

- **New target `nse_tls_kx_aead`:** any share into X448 and each FFDHE group

The leading-zero test first missed its sabotage: the secret it happened to
draw had no leading zero. It now searches for one. Against a real server,
keeping the zero would fail about one DHE handshake in 256.

**Found: a narrow regression, ledgered as `nse-tls-dhe-own-group`.**

- **Which servers:** ones that rank a DHE suite above every ECDHE suite the
  port offers (server cipher order) and use a DH group of their own.
- **Before step a:** the port offered no DHE, so such a server chose ECDHE
  and the handshake succeeded.
- **Now:** the server chooses DHE, and rustls refuses any group but RFC
  7919's. 7.94 checks the group and goes on.
- **Measured** by the new row `dhe-own2048-serverpref`.
- **Not affected:** a server that honours the client's order, or prefers
  ECDHE, or uses an RFC 7919 group.
- **Closes in step e,** with the server's own group under OpenSSL's checks.

**Not verified:**

- The constant-time claims are `crypto-bigint`'s and `ctutils`'s. No timing
  measurement was made here.
- CI's 60 s smoke reaches about 2,000 inputs of the new target.
