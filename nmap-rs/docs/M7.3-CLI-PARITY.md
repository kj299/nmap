# M7.3 — CLI parity triage: what "cutover" has to mean

`nmap-rs` implements 14 of C nmap's 100 long options and 8 of its 28 short ones.
Since M7.0 it **refuses** everything else and exits non-zero rather than scanning
anyway. That made the gap honest; it did not make it smaller. This document sorts
every unimplemented option into what must exist before cutover, what should, and
what may stay refused indefinitely — and uses that sort to answer the question M7
has been carrying since its first analysis.

Counts are measured, not remembered: the option table is `nmap.cc:525-640`, the
short-option string is the `getopt_long_only` call at `nmap.cc:653`, and the
implemented set is the `match` in `crates/core/src/options.rs:261`.

---

## 1. The answer to "what does cutover mean?"

`M7-ANALYSIS.md` §6 Q1 offered two choices: (a) a drop-in replacement for the
flags it supports, refusing the rest, or (b) full CLI parity first.

**Neither, and the dichotomy is the problem.** Both options measure cutover in
flags, and flags are the wrong unit.

* **(b) is not reachable.** 86 long options is not a milestone, it is a second
  project. A third of them are blocked behind subsystems this port has
  deliberately not built — NSE's Lua runtime (still undecided, and M6 is blocked
  on it), idle scan, proxies, host discovery. Full parity means building all of
  them first.
* **(a) is reachable and not worth reaching.** "A drop-in for the flags it
  supports" is true of any program if you choose the flags afterwards. An
  operator does not type a flag set; they type the invocation their runbook
  already contains, and `-iL targets.txt --exclude 10.0.0.5 -T4` is an ordinary
  one. Under (a) that is three refusals.

The unit that works is a **capability profile**: a written statement of the kind
of scanning `nmap-rs` is a genuine drop-in for, with everything outside it
refused. Proposed:

> **Cutover profile.** `nmap-rs` replaces `nmap` for *unauthenticated TCP and UDP
> port scanning of explicitly named targets, with service-version and OS
> detection, under operator-specified scope and rate limits.* It does not do host
> discovery, name resolution, scripting, or traffic obfuscation, and refuses every
> option that asks for them.

That profile is what the **MUST** tier below is derived from — it is exactly the
set of options an invocation inside the profile can reasonably contain. It is
finite (24 options), it is testable, and it can be written on the front page of
the README so nobody discovers the boundary by being refused.

The three exclusions are deliberate and worth stating as choices rather than
gaps:

* **No name resolution.** The port resolves nothing; `-n` is already accepted as
  a no-op for exactly that reason. `-R`, `--dns-servers` and `--system-dns` stay
  refused.
* **No scripting.** Blocked on the M6 Lua-runtime decision, which is still open.
* **No obfuscation.** Decoys, source spoofing, MAC spoofing, FTP bounce and
  fragmentation are a policy question, not a scheduling one — see §5.

## 2. MUST — 24 options the profile requires

Ordered by `scope_risk`: what would happen if the option were silently *ignored*
rather than refused. This is the axis the M7.0 bug lived on — `--exclude` was
believed harmless to ignore and in fact caused the named host to be scanned — so
it drives the order here.

### 2a. Scope constraints — ignoring them scans MORE (7)

| option | effect | effort |
|---|---|---|
| `--exclude <hosts>` | remove hosts from the target set | small |
| `--excludefile <file>` | same, from a file | small |
| `--exclude-ports <spec>` | remove ports from the scan | small |
| `--top-ports <n>` | scan only the n most common ports | medium — needs the frequency data from `nmap-services` |
| `-F` | fast mode: top 100 ports | small once `--top-ports` exists |
| `--port-ratio <r>` | ports more common than a ratio | small once the above exists |
| `--allports` | override `--exclude-ports` | trivial, and it must land *with* `--exclude-ports`, never before |

`--allports` is the one to watch. It exists to cancel a scope constraint, so
implementing it while `--exclude-ports` is still refused would ship a flag whose
only job is to widen a scan that was never narrowed.

### 2b. Rate and duration constraints — ignoring them scans FASTER (11)

| option | effect | effort |
|---|---|---|
| `-T<0-5>` | timing template; sets the whole group below | medium |
| `--scan-delay`, `--max-scan-delay` | floor/ceiling on inter-probe delay | small |
| `--max-retries` | cap probe retransmissions | small |
| `--host-timeout` | give up on a host after a duration | medium |
| `--min-parallelism`, `--max-parallelism` | outstanding probe count | medium |
| `--min-hostgroup`, `--max-hostgroup` | hosts scanned in parallel | medium |
| `--initial-rtt-timeout`, `--min-rtt-timeout`, `--max-rtt-timeout` | RTT bounds | small — `core::congestion` and `core::timing` already hold these values |

`-T` is the highest-value single item in this document. It is the option
operators actually reach for, it is the one most likely to appear in an existing
runbook, and in the C it is a *preset* over the other ten — so implementing it
means implementing them, and implementing them makes `-T` nearly free.

### 2c. Target specification — ignoring them scans something ELSE (2)

| option | effect | effort |
|---|---|---|
| `-iL <file>` | read the target list from a file | small |
| `-sL` | list scan: resolve and print targets, scan nothing | small |

`-sL` earns its place on a safety argument rather than a convenience one: it is
the dry run. It is how an operator checks what a target expression expands to
*before* scanning it, and a scanner that cannot be asked "what would you scan?"
is harder to use safely. It is also nearly free here — the target expansion
already exists, and `-sL` is that expansion with the scan skipped.

### 2d. Output the profile implies (3)

| option | effect | effort |
|---|---|---|
| `-oA <basename>` | write all three formats at once | trivial — `-oN`/`-oX`/`-oG` all exist |
| `--open` | report only open ports | small |
| `--reason` | report why a port is in its state | small — `Reason` is already carried through `core::classify` and rendered nowhere |

`--reason` is the odd one: the data is already computed and threaded all the way
to the output layer. Only the rendering is missing.

## 3. SHOULD — 21 options

Refusing these is honest but costs a user who is otherwise inside the profile.
None is required for cutover.

**Scan techniques the engine could carry**: `-sO` (IP protocol scan), `-sY`/`-sZ`
(SCTP), `--scanflags` (custom TCP flag combinations — the flag-scan machinery
already exists; this is exposing it).

**Output and reporting**: `-oS` (the joke format; trivial and listed because
`-oA` implies it in C), `--append-output`, `--stylesheet`, `--no-stylesheet`,
`--webxml`, `--packet-trace`, `--stats-every`, `-v`'s `--vv` alias, `-q`.

**Operational**: `-e <iface>` (choose the interface — `sys::netif` and
`sys::route` already enumerate and choose one, so this is an override, not new
machinery), `-g`/`--source-port`, `--iflist` (print interfaces and exit; a
diagnostic that would pay for itself), `--noninteractive`, `--datadir`,
`--servicedb`, `--versiondb`.

`--datadir`, `--servicedb` and `--versiondb` deserve a note: they point the
scanner at operator-supplied data files, which makes those files attacker-
influenced in exactly the way `core::sigstore` was built to handle. Implementing
them should go through the signature store rather than around it.

## 4. REFUSE — 51 options

Refusing indefinitely is the right answer for these, for four distinct reasons.
The reason matters more than the tier.

### 4a. Blocked on the NSE decision — 7

`--script`, `--script-args`, `--script-args-file`, `--script-help`,
`--script-trace`, `--script-updatedb`, `--script-timeout`, `-sC`.

Not a judgement about scripting; a consequence of M6 being blocked at the
Lua-runtime decision. M6.1 and M6.2 ported the script index and the `--script`
selection grammar precisely because they are independent of it, so the parsing
half of NSE already exists. These 8 stay refused until that decision is made.

### 4b. Blocked on a subsystem this port has not built — 15

Idle scan (`-sI`), FTP bounce (`-b`), proxies (`--proxies`, `--proxy`),
host discovery (`-sn`, `-PS`/`-PA`/`-PU`/`-PY`/`-PE`/`-PP`/`-PM`/`-PO` via `-P`,
`--disable-arp-ping`, `--discovery-ignore-rst`), name resolution (`-R`,
`--dns-servers`, `--system-dns`, `--resolve-all`), `--traceroute`,
`--nsock-engine`, `--route-dst`, `--resume`.

### 4c. Deliberately declined — see §5 — 15

`-D` (decoys), `-S` (spoof source address), `--spoof-mac`, `-f`/`--ff`/`--mtu`
(fragmentation), `--badsum`, `--data`, `--data-string`, `--data-length`,
`--ip-options`, `--ttl`.

### 4d. Deprecated, internal, or already parity — 14

| option | why |
|---|---|
| `--oH` | **C nmap already refuses it** — `nmap.cc:902` calls `fatal("HTML output is not directly supported…")`. Refusing it here is parity, not a gap. |
| `--thc` | an easter egg: prints greets and exits (`nmap.cc:916`) |
| `--nogcc`, `--adler32`, `--unique`, `--rH` (alias), `--randomize-hosts`, `--deprecated-xml-osclass`, `--privileged`, `--unprivileged`, `-M`, `-m`, `-I`, `--oM` | internal, deprecated, or superseded |

Two more were in this bucket and have **moved out of the refusal set entirely**
in this milestone — see §6.

## 5. The one question this triage cannot answer alone

§4c is not an engineering judgement and should not be made as one.

`-D`, `-S`, `--spoof-mac`, `--badsum`, fragmentation and custom payloads exist to
make a scan harder to attribute or harder to detect. C nmap has them; a
faithful port would too. But this port's stated purpose is to be *safer* than the
C, its threat model is written down, and "reproduce the evasion suite" is a
choice with consequences rather than a default.

There are two defensible positions and this document deliberately does not pick:

1. **Port them.** Parity is the goal; an operator doing authorised testing has
   legitimate need, and withholding them just sends that operator back to C nmap
   — which achieves nothing for safety.
2. **Decline them permanently.** State it in the README and in `DIVERGENCES.md`
   as a deliberate scope decision, so the boundary is a documented property
   rather than an unfinished edge.

They are classified REFUSE above because that is their status today either way.
The distinction between "not yet" and "not ever" needs an owner's decision.

## 6. Landed in this milestone

Reading the C for every option turned up three that need no implementation at
all, because the port's unconditional behaviour — or C nmap's own — already
satisfies them. All three now join `-n` in `options.rs`'s `ALREADY_SATISFIED`
carve-out, each with a code-checkable reason:

| option | why it qualifies |
|---|---|
| `-r` | "scan ports sequentially, don't randomise". This port never randomises: ports come out of `parse_port_spec` ascending and are sorted by `(protocol, number)` before reporting, which `sys::scan`'s own test already asserts. There is no randomisation to turn off. |
| `--release-memory` | **a no-op in C nmap too.** `nmap.cc:730` handles it with `/* No-op. We always release memory now. */`. |
| `--log-errors` | **deprecated and always-on in C nmap**, whose handler says it is "left in so as to not break anybody's scanning scripts". |

The last two are worth emphasising: accepting them is not a concession, it is
*exact parity*. Refusing them would make `nmap-rs` reject a command that C nmap
accepts and ignores.

The carve-out's guard rails hold. `the_no_op_carve_out_does_not_leak_to_its_opposite`
now also asserts that `--randomize-hosts` and its `--rH` alias — the opposite of
`-r` — are still refused, on the same principle that keeps `-R` refused beside
`-n`: the port cannot do what they ask.

### A parity gap in a feature that was already finished

Three more options left the refusal set, and this one was not a triage judgement
but a bug, found the same way M7.0's was — by running the binary rather than
reading it:

```console
$ nmap-rs -oN out.txt -sT -p 80 127.0.0.1     # works
$ nmap-rs --oN out.txt -sT -p 80 127.0.0.1
nmap-rs: unrecognized or unsupported option '--oN'
nmap-rs: refusing to scan — ...
```

C nmap accepts both spellings. `getopt_long_only` (`nmap.cc:653`) matches a long
option after a *single* dash, and `oN`/`oX`/`oG` are in the long-option table —
so `-oN f` and `--oN f` are the same command there. This port matched only
`starts_with("-oN")`, and `"--oN"` does not start with `"-oN"`. So three fully
implemented output formats were unreachable by their documented long spelling,
and the M7.0 fail-closed change turned that from a silent misparse into a
refusal — which is how it became visible at all.

Both spellings now reach the same field, attached or separate, pinned by
`output_flags_accept_both_the_short_and_long_spelling`.

The general point for the rest of the MUST tier: **every option in that tier has
two spellings**, and a `starts_with` on the short one silently misses the long.
Worth checking as each lands rather than discovering it three at a time.

Refusal surface: **102 → 96**, at zero behavioural risk and without implementing a
single new feature.

## 7. Proposed order

1. **`--exclude` / `--excludefile` / `-iL`.** The first two close the exact hole
   M7.0 found; `-iL` is the option most likely to appear in an existing runbook.
   All three are small and share target-set plumbing.
2. **`-sL`.** The dry run. Nearly free once §1 lands, and it makes the rest safe
   to test.
3. **The `-T` group.** One medium piece of work that delivers eleven options,
   because `-T` is a preset over the other ten and `core::congestion` /
   `core::timing` already hold the values.
4. **`--top-ports` / `-F` / `--port-ratio` / `--exclude-ports` / `--allports`.**
   Port-scope as one unit — and `--allports` must not land before
   `--exclude-ports`.
5. **`-oA` / `--open` / `--reason`.** Cheap, and `--reason` only needs rendering.

That is the MUST tier, in five steps, and its completion is the cutover gate.
